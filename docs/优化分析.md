# 优化分析

> 基于当前 Python 主路径（FastAPI + `app/workflow/orchestrator.py` + `app/web/static/app.js`）的梳理。  
> 更新日期：2026-07-16

---

## 一、性能优化

### 1.1 状态落盘频率偏高（高优先级）

**现状**：`stream_command_to_logs` 在 CLI 流式输出时通过 `_persist_state` 写完整 `state.json`；安静模式下约每 0.6s 合并一次，心跳约 30s 另写一次。

**影响**：代码生成/设计日志多时，磁盘 I/O 与 JSON 序列化成为瓶颈；`state.json` 体积随 `logs` / `codegen_progress` 增长后更明显。

**建议**：

- 进度类字段（`codegen_progress`、尾部 `logs`）与核心状态拆分存储，或限制日志条数/总字符上限
- 流式阶段仅写「轻量进度文件」，任务结束再合并进 `state.json`
- 对 `_persist_state` 做按会话的 debounce（例如 1～2s）并跳过无变化写入

### 1.2 前端轮询与列表刷新（中高优先级）

**现状**：

- 侧栏 `setInterval(loadProjectsList, 5000)` 每 5s 请求 `/api/sessions`
- 后端 `list_sessions` 每次遍历目录并 `read_text` 全部 `state.json`
- 代码生成 / H5 测试 / 发布 / 补充对话各有独立 `setInterval` 轮询（1.5s 量级）

**影响**：多标签页、多项目时请求叠加；SSE 已推送状态时仍重复拉全量会话列表。

**建议**：

- 侧栏列表改为 **SSE 驱动增量更新** + 较长间隔兜底（30～60s）
- `list_sessions` 只读摘要字段（`session_id`、`app_name`、`step`、`group_no`、`created`），避免解析完整大 JSON
- 同一页面合并轮询：一个 `pollSessionState()` 根据 `codegen_running` / `h5_test_running` 等标志决定是否继续

### 1.3 项目列表 DOM 与事件绑定（中优先级）

**现状**：历史上 `attachProjectListeners` 使用 `cloneNode` 替换容器以避免重复绑定；已部分改为事件委托，但定时刷新仍可能触发全量 `innerHTML` 重绘。

**建议**：

- 列表项仅 patch 变更字段（步骤徽章、高亮），避免整块 `innerHTML`
- 删除 `cloneNode` 路径，统一事件委托（与当前 `projectsList` 点击委托一致）

### 1.4 Stitch 设计并行与网络（中优先级）

**现状**：最多 3 路 `ThreadPoolExecutor` 并行调用 Stitch；单次 `generate_screen_from_text` 可达数分钟；下载 png/html 为串行 `get_screen` + HTTP 下载。

**建议**：

- 下载 4 屏资源改为会话内 **并行下载**（限制并发 2～4）
- 对 `invalid argument` 已做有限重试；下载可增加 **超时重试 + 断点跳过单屏**
- 并发数、超时、重试次数写入 `local_config.yaml` 可调

### 1.5 H5 测试进程与端口（低～中优先级）

**现状**：每会话分配 8100～8999 端口，测试前清空 `unpackage/dist`；进程登记在内存 `_session_procs`。

**建议**：

- 服务重启后清理孤儿 node/uniapp-cli 进程（启动时扫描端口占用）
- 端口分配持久化到 `state.h5_test_port`，便于重启后提示「端口可能仍占用」

### 1.6 编排器单文件过大（维护性 → 间接影响性能）

**现状**：`orchestrator.py` 集中状态机、Stitch、三种 CLI、发布、README、提示词等，单文件数千行。

**建议**：按领域拆模块（`design.py` / `codegen.py` / `release.py`），便于单独优化与测试，减少误改回归。

## 二、功能优化

### 2.1 设计引擎可插拔（规划中）

**现状**：设计仅 Stitch MCP；已规划 **Open Design** 作为本地替代（见对话备忘）。

**建议**：

- 抽象 `DesignEngine` 接口：`stitch` | `opendesign` | `skip`
- 产物统一落 `static/stitch/tab{1..4}.{html,png}`，下游代码生成无感切换
- 第 4 步增加第三路线「Open Design 本地设计」

### 2.2 单风格失败可重试（高价值）

**现状**：Stitch 某风格失败后任务标记 `failed`，需重新跑整套设计或手动换风格。

**建议**：

- 设计进度条对失败项增加 **「重试该风格」** 按钮
- 后端 `POST /api/session/{id}/retry-style?index=n`，复用已有 `project_id` 或新建项目

### 2.3 代码生成工具选择时机（已部分优化）

**现状**：第 4 步已移除工具选择；第 6 步「选择方案」与第 7 步可改工具。

**可继续**：

- 第 6 步确认方案时记住工具，第 7 步默认只读展示，减少误触
- 补充对话默认继承上次成功工具

### 2.4 第 8 步体验（中优先级）

**已有**：README 生成、H5 测试（独立端口）、Git 发布、关闭测试端口、Cursor 打开项目。

**可增强**：

- README 生成前在页面预览 Markdown
- 发布前 diff 摘要（变更文件数、体积）
- H5 测试失败时展示 `log_tail` 折叠面板（后端已返回，前端可展示）

### 2.5 会话与运维（中优先级）

**现状**：侧栏支持删除会话并杀进程；无批量清理、无归档。

**建议**：

- 「清理 30 天前已完成会话」管理动作
- `cli.py` 增加 `sessions prune`、`open-cursor <id>`
- 健康检查 `/api/health` 附带 stitch/llm/hbuilderx 探测子状态

### 2.6 错误恢复与可观测性（中优先级）

**现状**：`error` + `error_step` 支持回到环节；Claude 网关 400、Stitch `invalid argument` 已有友好文案。

**建议**：

- 前端错误区统一展示「建议操作」（重试 / 换工具 / 跳过设计）
- 结构化 `error_code` 字段，便于统计哪类失败最多
- 可选接入 `.runtime/feedback.json` 自动汇总失败模式

### 2.7 质量与测试（长期）

**现状**：`quality.py` 有基础检查；自动化测试覆盖少；Java 后端与 Python 能力漂移。

**建议**：

- 为 `build_design_prompt` / `build_codegen_prompt` 做快照测试
- Stitch client mock 集成测试
- 明确 Java 后端「只读兼容」或下线策略，避免双份文档与 API 不一致

### 2.8 安全与多用户（按需）

**现状**：`0.0.0.0` 监听时局域网可访问；无鉴权；`open-in-cursor` 等服务端执行本机命令。

**建议**：

- 内网部署加简单 token 或仅 `127.0.0.1`
- 敏感 API（删除会话、发布 Git、打开 IDE）可加确认或本机来源校验

## 三、建议落地顺序

| 阶段 | 项 | 预期收益 |
|------|-----|----------|
| **短期** | 合并前端轮询、列表摘要 API | 立刻减请求与 CPU |
| **短期** | 日志/进度与 state 拆分或截断 | 减 I/O、加快切换项目 |
| **中期** | 单风格设计重试、下载并行 | 提升 Stitch 成功率与确认方案速度 |
| **中期** | Open Design 双引擎（MVP） | 降低 Stitch 依赖与配额问题 |
| **长期** | orchestrator 拆分 + 自动化测试 | 可维护性与回归安全 |
