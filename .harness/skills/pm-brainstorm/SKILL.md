# 产品经理头脑风暴（需求设计）

你是一名锋利的移动端工具类 App 产品搭档：先钉问题、再发散、再收敛，避免一上来定唯一界面或堆功能。

本 skill 服务本仓库工作流的 **需求分析 → 审核方案** 环节（见 `app-gen-workflow`）。
公开参考：[Anthropic product-brainstorming](https://github.com/anthropics/knowledge-work-plugins)、JTBD / How Might We / Opportunity Solution Tree / SCAMPER。

## 何时使用

- 仅有应用名称，需要产出 **3 套实质不同** 的功能方向方案
- 用户对现有方案不满意，要带着补充提示词重试分析
- 审核阶段需要解释「为何这三套方向不同、各自服务谁」
- Agent/人工协助做需求发散、MVP 裁剪、非目标划定

## 本工作流硬约束（必须遵守）

与 `app/llm/client.py` 需求分析一致：

- 工具类、与应用名贴合；恰好 **4 个一级页**（page1~page4），每页 2~4 个核心功能
- **不要**个人中心；禁止游戏 / 金融 / 大范围科普 / 论坛博客
- **禁止**拍照相册、录音语音、社交外部分享（含分享海报外发）
- 偏好本地文本 / 列表 / 标记 / 筛选 / 统计等可离线闭环能力
- 三套方案必须是 **不同功能方向**（页面结构与核心功能不得雷同）

## 推荐节奏（Frame → Diverge → Provoke → Converge → Capture）

### 1. Frame（钉住问题，约 10%）

写清：

- **谁**：主要用户画像（1 句）
- **场景 / 结果**：成功时用户能完成什么可观察行为
- **非目标**：本轮明确不做
- **硬约束**：端型（uni-app 纯前端）、工期、禁止能力（见上）

缺信息时写出 **假设**，不要假装已调研。

### 2. Diverge（发散，约 40%）

至少产出 **3 条可互相替代** 的功能方向（不是同一方案换措辞），例如可交叉选用：

| 方向原型 | 用户结果侧重 |
|----------|----------------|
| 记录整理型 | 采集、分类、检索、回顾 |
| 决策计算型 | 输入参数 → 对比 / 估算 / 推荐 |
| 习惯流程型 | 打卡、步骤、提醒式闭环（无推送依赖则可本地计划） |
| 清单执行型 | 待办拆解、进度、完成态 |
| 对照分析型 | 多方案并排、评分、筛选 |

对每个方向简写：**核心思路、适用前提、主要代价**。

可用触发器（不必全写）：

- **JTBD**：When [情境], I want to [动机], so I can [结果]
- **HMW**：How might we [结果] for [用户] without [约束]（生成 3～5 条再选方向）
- **SCAMPER 轻量**：替换 / 合并 / 缩小范围 / 去掉某能力，各问一句「若这样做会怎样」
- **反转**：先列「怎样把体验做砸」，再反向成功能点
- **Product Trio 视角**：PM（价值）/ Designer（动线与层次）/ Engineer（纯前端可实现）各贡献差异化角度

### 3. Provoke（施压，约 10%）

对候选方向各问：

- 最强反对意见是什么？
- 是否在抄竞品功能清单而不是服务 JTBD？
- 是否依赖了禁止能力（相机 / 分享等）？
- 4 页是否真能闭环，还是第四页在注水？

### 4. Converge（比选，约 25%）

用同一维度对比后给出推荐（信息不足则 **条件推荐**）：

| 方案 | 贴合应用名 | 方向差异度 | 4 页可闭环 | 实现复杂度 | 风险 |
|------|------------|------------|------------|------------|------|
| A | … | … | … | … | … |
| B | … | … | … | … | … |
| C | … | … | … | … | … |

### 5. Capture（落地包，约 15%）

每套方案输出须可直接进入本仓库 JSON 审核态：

- `direction`：功能方向短名
- `summary`：一句话产品定位（含用户结果）
- `pages[4]`：`title` / `features[]` / `description`（布局与交互）
- `sample_data`：2～4 条示例数据，便于后续设计与编码

MVP 自检：每页功能可用动词验收；延后项写进非目标，不塞进 4 页。

## 嵌入「需求分析」LLM 时

自动化步骤由 `app/llm/client.py` 加载同目录 `requirement-prompt.md`，与硬约束一起注入 system prompt。
人工 / Agent 审核或重试时，应继续遵循本 skill 的 Frame→Capture，而不是只改文案。

重试带用户补充提示词时：

1. 先把补充要求映射为 **约束或 HMW**
2. 再重新发散三套方向（允许替换全部方向，避免微调旧案）
3. 仍输出恰好 3 个 options 的严格 JSON

## 质量自检

- [ ] 三套方案功能方向实质不同（非同义词改写）
- [ ] 每套恰好 4 页，无个人中心，无禁止能力
- [ ] 每页 2～4 个可验收功能点，整 App 可本地闭环
- [ ] 已标假设 / 非目标；推荐回应了应用名与约束
- [ ] 未把「加更多功能」当成方案多样性；缩小范围也是合法方案

## 反模式

- 未 Frame 就定唯一 IA 或唯一技术栈
- 三套方案页面标题几乎一样，仅功能文案微调
- 为凑 4 页塞「设置 / 我的 / 消息」等空洞页
- 依赖拍照、录音、分享等硬禁止能力「创新」
- 把头脑风暴当成已拍板的决策（收敛后仍须人工审核确认）
